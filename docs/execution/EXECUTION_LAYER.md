# Execution Layer

`ExecutionManager` receives an `ExecutionRequest`, a broker-issued identity, and the ID of an ACP assignment. It verifies the assignment and role, limits concurrency to two by default, serializes turns in the same directory, persists state in the ACP SQLite database, and dispatches to the registered adapter. The adapter cannot publish ACP messages. On process success, the manager stores the final text as an artifact and publishes `ARTIFACT_SUBMITTED` or `FINDING_REPORTED` with the broker-issued identity.

The manager accepts only existing directories under explicit `allowed_roots`. `workspace-write` also requires an agent ID in `writable_agents` and an ACP assignment with `metadata.workspace_write=true`. Local POSIX file locks bind each execution and workspace across manager processes. Reconciliation skips an execution whose lock is still held. Different workspaces may run concurrently. The adversarial methodology creates its Git worktrees before dispatch; the generic manager does not choose Git repositories or create worktrees. These locks require a shared local filesystem and do not coordinate workflow schedulers or remote hosts.

An exit code of zero means that the Codex process finished and produced a final message. It does not approve the engineering work. QA must return JSON with `severity` and `description`; the manager validates these fields before publishing a finding. Severity remains the QA agent's assessment, not a deterministic quality gate.

The manager records failures without publishing an agent-originated `TASK_FAILED`, which the ACP reserves for the orchestrator. Workflows and quality gates remain outside this layer.

## Recuperação após perda do manager

Quando o manager perde uma execução ativa, `ExecutionRepository.reconcile()` grava `INTERRUPTED`. O status não autoriza repetir o turno. `ExecutionManager` recusa novas execuções no mesmo workspace e em caminhos que se sobreponham a ele. A quarentena continua após reinício porque o SQLite guarda o status e a reconciliação.

O adapter Codex registra PID, PGID, boot e instante de início do processo quando disponíveis. `ExecutionRepository.process_info(execution_id)` fornece esses dados ao operador. Um operador configurado em `local_operators` pode chamar `ExecutionManager.reconcile_execution(execution_id, actor, evidence, effects_status="UNKNOWN", confirm_workspace_inspected=True)` depois de verificar os processos e a integridade do workspace. `effects_status` deve ser `VERIFIED`, `REVERTED` ou `UNKNOWN` e descreve a avaliação dos efeitos externos pelo operador; não transforma o turno em sucesso. Toda liberação exige confirmação e evidência textual, mesmo quando o grupo registrado não existe mais. Um boot ID diferente evita atribuir um grupo atual à inicialização anterior. No mesmo boot, um grupo presente mantém a quarentena mesmo se o PID indicar outro instante de início: esse dado ajuda a inspeção, mas não prova que descendentes antigos terminaram. A reconciliação fica em `execution_reconciliations`; o turno original permanece `INTERRUPTED`. Se um processo filho permanecer no grupo após a saída normal do Codex, o turno também termina como `INTERRUPTED` e o workspace fica em quarentena.

O AEC não encerra grupos automaticamente após reinício. Um descendente pode sair do grupo antes da verificação. A lista local de operadores não autentica pessoas remotamente. A liberação exige inspeção real pelo operador e não equivale a isolamento de sistema operacional.

### Supervisão opcional por scope do systemd

Em Linux com `systemd --user`, `CodexCliAdapter(policy=policy, supervise_with_systemd=True)` executa cada turno em uma scope exclusiva com nome aleatório `aec-<hex>.scope`. O manager persiste o nome da unidade e o boot ID antes de iniciar o subprocesso. O adapter mantém os streams do Codex e não lê nem copia credenciais. Se a unidade não puder ser registrada, o turno não é iniciado. O healthcheck exige um user manager acessível; a ausência dessa condição não aciona fallback silencioso.

Na conclusão, cancelamento e reconciliação, o repositório consulta a scope além do PGID. Unidade ativa, estado desconhecido ou falha na consulta preservam `INTERRUPTED` e a quarentena. Após queda do manager, a unidade pode conter descendentes que saíram do PGID; a execução original nunca é repetida automaticamente. Mesmo com a unidade vazia, a liberação requer inspeção do workspace, avaliação de efeitos externos e evidência humana. Um boot ID diferente evita consultar uma unidade homônima de outra inicialização, mas não dispensa a reconciliação.

O modo por PGID continua disponível para sistemas sem `systemd --user`. A scope melhora a supervisão de processos cooperativos; processos com permissão para migrar para fora do cgroup e efeitos externos já produzidos continuam fora da garantia. Não é sandbox para código não confiável. O teste de `SIGKILL` e o teste de filho que chama `setsid()` usam executores simulados; um turno Codex real somente leitura também passou em scope. Evidência em `.audit/local-supervision-verification.txt`.
